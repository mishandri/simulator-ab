# Симулятор A/B тестов

Интерактивный тренажёр для обучения проведению A/B тестов: вы формулируете
гипотезу, выбираете метрику, считаете размер выборки, ведёте эксперимент
и принимаете решение о выкатке — а в конце получаете разбор каждого решения.

Статический сайт на GitHub Pages. Без сборки, без зависимостей, без бэкенда.

---

## Что внутри

- **3 сценария** с разными ловушками: подглядывание в мониторинг, прокси-метрика
  вместо бизнес-метрики, сломанный рандомайзер (SRM), конфликт основной метрики
  и гвардрейла.
- **Живой эксперимент**: график накопительной конверсии по дням, текущие значения
  метрик и p-value — ровно то, что видел бы аналитик, и ничего больше.
- **Честная статистика**, реализованная с нуля:
  - z-тест для долей с доверительными интервалами;
  - t-тест Уэлча для средних (через неполную бетта-функцию);
  - хи-квадрат и проверка SRM;
  - расчёт MDE, мощности и размера выборки;
  - неполная гамма-функция и функция Ланжеса — база для всех p-value.
- **Тесты** ([`tests.html`](tests.html)): 55 проверок против эталонных значений,
  посчитанных независимой реализацией на Python.

## Ключевые решения

**Трафика намеренно мало.** В сценариях 1 500–2 500 сессий в день, чего
заведомо не хватает на эффект в несколько процентов. Это сделано ради одного
урока: **объём данных задаётся сроком и трафиком, а не MDE**. MDE — не кнопка
«сделать тест точнее», а цена, которую вы платите трафиком (размер выборки
растёт как 1/MDE²). Если бы трафика было много, вопрос про мощность всегда
давал бы 100% и перестал что-то учить.

**Четыре рычага вместо одного.** MDE, доля трафика на B, длительность и уровень
значимости. Под каждым ползунком — подсказка, что двигать и почему, с числами.
Срок задаётся кратно неделе (7…56 дней): у трафика и конверсии есть недельная
цикличность, поэтому тест на 10 дней хуже, чем на 14, а не просто «меньше».
Это позволяет разобрать настоящий размен: при фиксированном трафике мощность
растёт линейно со сроком, а требования к MDE — квадратично.

**Два разных срока.** «Срок по объёму данных» — сколько нужно набрать под
заявленный MDE. Выбранный срок — сколько дней вы готовы держать тест.
Отсюда и подсказка: если нужного объёма не набрать даже за максимум ползунка,
подсказка прямо говорит «срок упёрся в потолок, поднимите MDE», а не советует
недостижимое.

**Мощность считается на реальном объёме, а не на нужном.** Фраза
«мощность 80%» относилась бы к объёму, подобранному под этот же MDE, то есть
сравнивала бы 80% с 80%. Поэтому в интерфейсе:
- *мощность на вашем MDE* — хватит ли данных под вашу планку;
- *мощность на типичном эффекте* — вот это и есть настоящий вопрос;
- *эффект, который тест надёжно отличит от нуля* — обратная задача.

Подсказка срока намеренно может быть зелёной при красном выводе: срок достаточен
по **вашному** MDE, но не по **реальному** эффекту. Это разные утверждения, и
путать их — источник большинства ошибок в планировании тестов.

**Мощность — не то же самое, что достижимость MDE.** Это два независимых
вопроса, и в интерфейсе они разведены:

| Вопрос | От чего зависит | Как влияет срок |
|---|---|---|
| Хватает ли данных под заявленный MDE? | от MDE и трафика | влияет |
| Поймает ли тест реальный эффект? (мощность) | от объёма данных и размера эффекта | влияет |

Отсюда неочевидный вывод, который тренажёр проговаривает прямо: **поднять MDE,
чтобы «добрать мощность», невозможно**. Крупный MDE снижает требование к объёму,
но не увеличивает способность теста увидеть настоящий эффект.

**Допуск к мощности** (`POWER_TOL`). 79.8% и 80% — практически одно и то же, но
без допуска интерфейс показывал «мощность 80.0%» и тут же красное «мощности не
хватит». Округление вверх создавало видимое противоречие.

## Почему без базы данных

GitHub Pages умеет только статические файлы, поэтому «БД» здесь не нужна:

| Что | Где живёт | Почему так |
|---|---|---|
| Параметры сценариев | `src/scenarios.js` (версионируется в репозитории) | Сценарий — это контент, а не данные |
| Данные эксперимента | генерируются в браузере по фиксированному `seed` | Один и тот же сценарий всегда даёт одну и ту же историю — результат можно обсуждать и повторять |
| Прогресс и ошибки | `localStorage` | Не нужна синхронизация между устройствами |

Альтернативы и почему они не выбраны: GitHub API как «read-only БД» (лимит
60 запросов в час без токена, запись невозможна), Supabase/Firebase (отдельная
инфраструктура ради лидерборда, которого пока нет). Если позже понадобится
общая статистика прохождений — подключать её точечно, не переделывая ядро.

## Локальный запуск

Node не нужен — только Python для статического сервера:

```bash
python tools/serve.py 8777     # → http://127.0.0.1:8777/
```

Открыть `index.html` напрямую файлом нельзя: браузер запрещает ES-модули по `file://`.

## Публикация

## Как добавить сценарий

Дописать объект в `SCENARIOS` в `src/scenarios.js`:

```js
{
  id: 'my-case',
  title: 'Что проверяем',
  difficulty: 2,
  teaser: 'Одна фраза для выбора сценария.',
  product: 'Название продукта',
  hypothesis: 'Задание от заказчика.',
  seed: 12345,                  // меняет данные, но не структуру
  goodPrimary: ['conversion'], // что следовало выбрать основной метрикой
  guardrails: ['arpu'],         // что блокирует выкатку при падении > 10%
  trafficPerDay: 1500,          // намеренно мало: мощность должна быть ограничением
  baselineConversion: 0.1,
  baselineCtr: 0.24,
  baselineRevenuePerUser: 45,
  truth: {
    condConversionLiftRel: 0.06, // эффект на P(покупка | клик)
    ctrLiftRel: 0.02,            // эффект на кликабельность
    revenuePerOrder: 0,          // эффект на средний чек
    novelty: 0.35,               // насколько эффект сильнее в первые дни
  },
  traps: {
    srm: false,          // чинить рандомизацию
    srmShareB: 0.58,     // сколько трафика реально уходит в B
    slowStart: false,    // первые дни показания скачут
  },
  durationDays: 21,      // срок по умолчанию; ученик может выбрать 7…56
}
```

Обратите внимание: `realizedConversionLift()` зависит от длительности. Эффект
новизны сильнее в начале, поэтому на коротком тесте (7 дней) средний эффект
заметно выше, чем на длинном (56 дней). Это не баг, а одна из причин, почему
сравнивать результаты тестов разной длительности напрямую нельзя.

Маржинальная конверсия раскладывается на два слоя:
`конверсия = CTR × P(покупка | клик)`. Именно из-за этой мультипликативной
структуры прокси-метрика может расти, а бизнес-метрика — стоять на месте.

## Как проверять изменения статистики

1. `python tools/reference.py` — пересчитать эталонные значения.
2. Открыть `tests.html` и убедиться, что все проверки проходят.

Эталонные числа считаются **независимой** реализацией на Python
(`math.erf` + регулярные аппроксимации неполной гамма- и бета-функций).
Если обе реализации сходятся до 1e-12, вероятность общей ошибки в формуле
практически нулевая.

## Ограничения прототипа

- Расчёт MDE и размера выборки делается по базовой конверсии, даже если основная
  метрика — среднее (ARPU). Для обучения достаточно, для продакшна — нет.
- Последовательные тесты (Always Valid, mSPRT) не реализованы: симулятор
  учит фиксировать срок и ждать, а не правильно останавливаться досрочно.
- Нет распределённых метрик (留存, LTV), когортного анализа и CUPED.
- `timeOnSite` в интерфейсе есть, но не симулируется — как и любая метрика,
  которую пришлось бы придумать, а не вывести из данных.
